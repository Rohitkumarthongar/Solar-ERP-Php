# Production deployment

This optional Compose deployment builds the PHP/Apache application and Vite assets from the checked-in lockfiles, installs Chromium and the production Puppeteer runtime for PDF generation, starts MariaDB 11.4, and keeps database and Laravel storage in named volumes. It binds HTTP only to `127.0.0.1:8080`; put a TLS-terminating reverse proxy on the same host in front of it. Do not expose port 8080 directly. Docker Engine with Compose v2, outbound access to the image/package registries during build, DNS, a public TLS certificate, and durable disk space for the volumes and backups are required.

## Prepare

1. Create a private `.env` from `.env.example` on the deployment host. Set a strong `APP_KEY` with `php artisan key:generate --show` in a trusted environment, a public `APP_URL=https://your-hostname`, `DB_DATABASE`, a non-root `DB_USERNAME` and strong `DB_PASSWORD`, and `TRUSTED_ADMIN_EMAILS` to the comma-separated real email addresses of the authorized administrators. Keep this file outside backups shared with untrusted parties; never commit it. Compose sets `APP_ENV=production`, `APP_DEBUG=false`, `DB_CONNECTION=mysql`, `CACHE_STORE=database`, `QUEUE_CONNECTION=sync`, `SESSION_DRIVER=database`, and `SESSION_SECURE_COOKIE=true` regardless of the local defaults in `.env.example`.
2. Configure the reverse proxy to forward to `http://127.0.0.1:8080`, enforce HTTPS and redirect HTTP, forward the original `Host` and `X-Forwarded-Proto`, and enable HSTS once HTTPS works. Configure Laravel's trusted proxy addresses for the actual proxy topology before serving traffic; never trust arbitrary client-supplied forwarded headers. Check that login sets a `Secure`, `HttpOnly` session cookie and that generated links use HTTPS. Restrict admin access at the network/proxy layer where practical.
3. Build and start with `docker compose up -d --build`. Once the database is healthy, run `docker compose exec app php artisan migrate --force` and `docker compose exec app php artisan storage:link` (the link exposes public branding/blog images only). Migrations must be reviewed and a restorable backup taken before running them on an existing deployment. Inspect `docker compose logs app db` and test the public site and login through HTTPS.

The production seed command is **not** a bootstrap mechanism: the seed data contains example business records. After migrations, run `docker compose exec app php artisan admin:bootstrap administrator@example.com`, replacing the example with an email in `TRUSTED_ADMIN_EMAILS`. It only creates the first account and privately prompts for a confirmed strong password; do not pass passwords on the command line or publish them. Grant other accounts only the roles they need. Do not enable the demo identities in production. The allowlist controls privileged settings/user administration, not ordinary login authentication.

The Compose queue uses `sync`, so work runs during the request; switching to `database` requires an independently supervised `php artisan queue:work` process, an appropriate jobs table, and worker monitoring. `MAIL_MAILER=log` is suitable only while outbound delivery is intentionally disabled; configure and verify the approved mail/SMS providers separately before expecting acknowledgements. Do not paste provider secrets into documentation.

## Backups and legacy data

Take regular consistent MariaDB dumps/snapshots and retain the `db_data` volume, the `app_storage` volume, and the private `.env`/APP_KEY in encrypted, access-controlled backups. Store copies off-host, define retention, and periodically test restoration to a separate environment. Database rows encrypted with APP_KEY cannot be restored meaningfully without the matching key. Schedule backups before every upgrade; stop writes or use transaction-consistent snapshots for database and files together.

Before migrating an existing installation, inventory any legacy uploads in its old bind-mounted `storage/app`, `public/storage`, or other application-managed locations, including private PDFs and customer attachments. Map each old path and DB reference to the new private `app_storage` mount (`/var/www/html/storage`), preserve file ownership for `www-data`, and verify read access and download authorization on a staging copy. Do not blindly copy an old public upload tree into the web document root: move private files to private storage and adapt references/access paths as needed. Preserve a separate private backup of the source and compare counts/checksums before cutover. A new image rebuild does not import legacy files automatically. Do not run migrations or transfer live data until the backup and cutover plan is approved.
